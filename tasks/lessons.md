[2026-09-21] `ROADMAP.md` présente encore `OpenAiCompatProvider` comme à faire alors que `OpenAiCompatibleProvider` est implémenté et appelé par les commandes de traduction → Le suivi documentaire et le code divergent (constat vérifié en lecture, origine de la divergence non déterminée) → Avant de refaire une fonctionnalité, rapprocher roadmap, code, historique et preuves ; distinguer présence du code et validation réelle. Voir `docs/journal/2026-09-21-continuite-codex-claude.md`.

[2026-06-11] Wolf RPG v3.x (Inko) `.mps`/`CommonEvent.dat` support via fork-surgery on `wolfrpg-map-parser` was abandoned mid-implementation → Root cause: v3.x's LZ4-wrapped header + WolfTL's flat, non-recursive `Command::Init` model (with a v3.5+ `v35Unknown` trailer per command) diverges too far from `wolfrpg-map-parser`'s recursive v2.x-shaped container model — patching it on top would require invasive upstream changes for a format the crate was never designed for → Rule: v3.x (Inko) parsing/writing lives in an in-house module (`src-tauri/src/engines/wolf/v3_format/`) ported byte-for-byte from WolfTL's flat model (MIT, github.com/Sinflower/WolfTL), validated via byte-exact `parse(bytes).dump() == bytes` round-trip on real files before wiring into extractor/injector. v2.x (Honoka) continues to use `wolfrpg_map_parser` — do not try to unify the two formats under one parser. **Mise à jour 2026-10-25 :** `wolfrpg-map-parser` (et son fork, supprimé de GitHub) a été retiré sur décision utilisateur ; v2.x n'est plus lu (refus explicite `UnsupportedWolfFormat`) en attendant une nouvelle lecture (lot RW). Ne pas réintroduire une dépendance Git vers un fork : un clone neuf doit compiler sans cache local.

[2026-06-13] `extract_dat_pairs_from_archives` mapped `.wolf` archive entries by filename stem only (`legacy_xor::WolfFile` had no path) → Root cause: some Wolf RPG games bundle a duplicate copy of `Data/BasicData/*.dat` inside a nested "sample data" folder (e.g. `データ集/（完全初期状態データ）/Data/BasicData/`); with only a basename, both copies collided in the same `HashMap` entry and the bogus nested copy (often with an invalid/truncated header) won, surfacing as a spurious "encrypted database" error for `DataBase.dat` and a *silent* truncated-segment bug for `CDataBase.dat` (whose bogus copy also has a valid-looking header) → Rule: when mapping archive entries to logical files by name, always disambiguate by full path when the archive format supports reconstructing it (DXA v8's `DARC_DIRECTORY` table does, via the same parent-chain walk already used for per-file key derivation) — never assume a filename is unique within an archive.

[2026-06-11] `llm/pipeline.rs::translate_batch` tokenized every project with `TokEngine::MvMz` regardless of `project.engine` → Root cause: the pipeline never threaded the project's engine through, so Wolf-only codes (`\E`, `\cself[n]`, `\r[Base,Ruby]`, `<L>/<C>/<R>`, etc. — verified ~28 of ~41 Wolf codes are NOT in `RE_MVMZ`) were sent raw to the LLM with no preservation instruction and silently dropped; `Tokenizer::validate`/`restore` couldn't catch it because the placeholder map was empty from the start → Rule: always set `TranslationContext.engine` from `projects.engine` and call `Tokenizer::tokenize(text, Engine::from_project_engine(&context.engine))` — this is the single source of truth, also reused by `core/qa.rs::check`.

[2026-06-14] `SettingsModal` reopened after a save showed stale/default values (theme, batch size, etc.) instead of the just-saved ones → Root cause: the modal stays mounted (`if (!open) return null` after hooks), and `draft`/`originalSettings` were initialized via `useState(currentSettings)` — that initial value is captured once at first mount, which happens before `App.tsx`'s async `loadSettings()` resolves, and is never re-applied after `saveSettings` updates the store → Rule: any modal/panel that stays mounted and seeds local draft state from a Zustand store must re-sync that draft (via `useEffect` keyed on the `open`/visibility prop) every time it opens, not just on first mount — `useState(storeValue)` only captures the value at that single render.

[2026-07-02] `git add -A` in a scoped Phase-8 commit swept in an unrelated pre-existing untracked file (`docs/prompt-remediation.md`, listed as `??` at session start), landing it on `main` via the merge → Root cause: used the blanket `git add -A` instead of staging the explicit paths the task touched, so any untracked file in the tree gets captured silently → Rule: when other untracked files exist in the working tree, stage explicit paths (`git add <path> …`), never `git add -A`/`git add .`; run `git status`/`git diff --cached --stat` before committing to confirm the staged set matches the task scope.

[2026-10-15] Tests Rust d'une revue de PR en échec « No space left on device » → `CARGO_TARGET_DIR` placé dans `/tmp`, qui est un tmpfs de 7,8 Go en RAM sur cette machine ; un build complet + tests dépasse 7 Go → Placer toute cible Cargo de build complet sur `/home` (ex. `~/.cache/<nom>-target`), jamais dans `/tmp`, et la supprimer après usage. Voir `docs/journal/2026-10-15-revue-pr-arcofrio.md`.

[2026-10-25] Copier des jeux de test dans `test/_session2/games/` pendant que `pnpm tauri dev` tourne a provoqué un `page reload` Vite de la webview (fichiers `index.html` du jeu surveillés) ; un projet créé juste après a reçu `target_language = fr` au lieu du `en` des réglages → Vite surveille tout le dépôt, y compris `test/` (ignoré par Git mais pas par Vite) ; cause exacte du `fr` non établie (repli backend `DEFAULT_TARGET_LANG`) → Pour les essais sur jeux réels avec l'app de dev, préparer les copies de jeux **avant** de lancer l'app, ou hors du dépôt ; après toute copie, vérifier `projects.target_language`. Voir `docs/audit/2026-10-analyse-complete.md`, P-9.

[2026-10-25] Règle utilisateur : `test/` ne doit **jamais** aller dans Git (jeux réels, copies de session, zips, preuves, scripts). Déjà ignoré (`.gitignore:29`, `test/*`) ; vérifié : aucun fichier suivi ni dans l'historique → Ne jamais `git add -f` sous `test/` ; avant un commit, ne pas recopier en masse dans les fichiers suivis du contenu venant de `test/` (texte des jeux) sans accord.

[2026-10-25] Copier le dossier d'un jeu déjà ouvert (avec `.hoshi2star.json`) rouvre le projet de l'original : `game_path` reste l'original et l'export y écrirait `hoshi2star.zip` → restauration par manifeste sans comparaison de chemin (S-C4) → Pour tout essai sur copie d'un projet ancien, réécrire `projects.game_path`, `source_files.file_path` et `gamePath` du manifeste vers la copie (base copiée seulement) **avant** le premier export. Voir P-8.

[2026-10-25] Tester un export MV/MZ « en jeu » sans Wine : les jeux MV/MZ sont du HTML5 → servir la copie (`www/` en MV, la racine en MZ) avec `python3 -m http.server` (config `ingame-*` de `.claude/launch.json`, non suivie) et la jouer dans le navigateur intégré ; lire `$gameMessage.allText()/faceName()/speakerName()/choices()`, `ImageManager.isReady()`, console et réseau plutôt que des captures ; `Scene_Splash` MZ attend un clic ; `Input._currentState.ok` pour avancer. Limite : pas de NW.js (plugins `nw.gui`/`fs`). Voir rapport, « Essais en jeu ».

[2026-10-25] Les probes de l'audit du 2026-09-05 ne compilaient plus sur `main` (`TranslationContext`, `QaSemanticContext`, `AppState`, `export_project` changés) et affirmaient les défauts : impossibles à relancer telles quelles → probes d'audit écrites comme tests à assertions, archivées hors de `src-tauri/tests/`, sans suivi de l'API → Écrire les probes d'audit en mode **observationnel** (afficher `PROBE <id>: …`, pas d'assertion sur le défaut), archiver avec la commande exacte de relance, et les adapter avant de conclure « corrigé » sur un échec de compilation. Voir `docs/audit/2026-10-analyse-complete.session3.probes.rs`.

[2026-10-25] Le gate complet (cargo clippy + cargo test + pnpm test, plus le hook pre-commit) lancé sur le poste de l'utilisateur a fait geler son PC, deux fois interrompu → builds Rust et tests en parallèle trop lourds pour cette machine pendant une session de travail → Ne plus lancer de build, clippy ni de suite de tests sur le poste local : pousser la branche et faire tourner le gate dans une session cloud. Le hook pre-commit lance aussi clippy : demander avant tout `--no-verify`. Lecture seule (git, rg, sqlite) reste locale.

[2026-10-26] Une garde d'export « valeur d'origine = source enregistrée » aurait laissé passer P-2 : la copie de référence, reconstruite après la mise à jour du jeu, remettait déjà la source japonaise sous le pointeur décalé (nom de visage) → la garde comparait à une copie dérivée de ce qu'elle devait contrôler (règle `stale_export` sans contrôle du rôle) → Tester toute garde contre la reconstruction réelle (test d'intégration par `open_project` + fichier modifié sur disque + `export_project`), jamais contre une copie fabriquée à la main ; une reconstruction ne modifie une valeur que si son rôle (commande, paramètre) est inchangé. Voir `docs/journal/2026-10-26-r2a-garde-source-export.md`.

[2026-10-26] Gate cloud impossible : `lindera-ipadic` télécharge son dictionnaire depuis `lindera.dev` au build, refusé (403) par la politique réseau de l'environnement → dépendance réseau cachée dans un build script → Avant un gate cloud, vérifier que `lindera.dev` est autorisé (accès réseau de l'environnement) ; `DOCS_RS=1` permet de compiler et de tester hors analyseur japonais (dictionnaire factice, 2 tests en échec attendus), mais ne vaut pas gate.

[2026-10-26] Gate RW-4 rouge sur `wolf_v2_game_is_refused_at_open` (`src-tauri/tests/e2e_project_flow.rs`) : en retirant `WOLF_V2_UNSUPPORTED`, le test d'intégration qui comparait la chaîne littérale `"wolf_v2_unsupported"` n'a pas été mis à jour → la recherche des usages portait sur le nom de la constante, pas sur sa valeur, et les tests d'intégration réutilisent la valeur en dur → Avant de retirer ou renommer un marqueur, une erreur ou un message, chercher son nom ET sa valeur littérale dans tout le dépôt (`src-tauri/src`, `src-tauri/tests`, `src/`), et faire importer la constante par les tests d'intégration plutôt que recopier sa valeur. Voir `docs/journal/2026-10-26-rw-wolf.md`.

[2026-10-26] Relance du gate RW-4 rouge : le nouveau test e2e `wolf_v2_game_opens_with_its_dialogue` lisait `project.engine` / `project.id` sur le retour d'`open_project`, qui est un `OpenProjectResult { project, was_restored }` (3 erreurs E0609) → type de retour supposé d'après le nom de la commande, sans lire sa signature ni les autres appels du même fichier (`.project` aux lignes voisines) → Sans compilation locale, avant d'écrire un appel dans un test, lire la signature exacte de la fonction appelée et copier la forme d'un appel existant du même fichier. Voir `docs/journal/2026-10-26-rw-wolf.md`.
