[2026-06-11] Wolf RPG v3.x (Inko) `.mps`/`CommonEvent.dat` support via fork-surgery on `wolfrpg-map-parser` was abandoned mid-implementation → Root cause: v3.x's LZ4-wrapped header + WolfTL's flat, non-recursive `Command::Init` model (with a v3.5+ `v35Unknown` trailer per command) diverges too far from `wolfrpg-map-parser`'s recursive v2.x-shaped container model — patching it on top would require invasive upstream changes for a format the crate was never designed for → Rule: v3.x (Inko) parsing/writing lives in an in-house module (`src-tauri/src/engines/wolf/v3_format/`) ported byte-for-byte from WolfTL's flat model (MIT, github.com/Sinflower/WolfTL), validated via byte-exact `parse(bytes).dump() == bytes` round-trip on real files before wiring into extractor/injector. v2.x (Honoka) continues to use `wolfrpg_map_parser` — do not try to unify the two formats under one parser.

[2026-06-13] `extract_dat_pairs_from_archives` mapped `.wolf` archive entries by filename stem only (`legacy_xor::WolfFile` had no path) → Root cause: some Wolf RPG games bundle a duplicate copy of `Data/BasicData/*.dat` inside a nested "sample data" folder (e.g. `データ集/（完全初期状態データ）/Data/BasicData/`); with only a basename, both copies collided in the same `HashMap` entry and the bogus nested copy (often with an invalid/truncated header) won, surfacing as a spurious "encrypted database" error for `DataBase.dat` and a *silent* truncated-segment bug for `CDataBase.dat` (whose bogus copy also has a valid-looking header) → Rule: when mapping archive entries to logical files by name, always disambiguate by full path when the archive format supports reconstructing it (DXA v8's `DARC_DIRECTORY` table does, via the same parent-chain walk already used for per-file key derivation) — never assume a filename is unique within an archive.

[2026-06-11] `llm/pipeline.rs::translate_batch` tokenized every project with `TokEngine::MvMz` regardless of `project.engine` → Root cause: the pipeline never threaded the project's engine through, so Wolf-only codes (`\E`, `\cself[n]`, `\r[Base,Ruby]`, `<L>/<C>/<R>`, etc. — verified ~28 of ~41 Wolf codes are NOT in `RE_MVMZ`) were sent raw to the LLM with no preservation instruction and silently dropped; `Tokenizer::validate`/`restore` couldn't catch it because the placeholder map was empty from the start → Rule: always set `TranslationContext.engine` from `projects.engine` and call `Tokenizer::tokenize(text, Engine::from_project_engine(&context.engine))` — this is the single source of truth, also reused by `core/qa.rs::check`.

[2026-06-14] `SettingsModal` reopened after a save showed stale/default values (theme, batch size, etc.) instead of the just-saved ones → Root cause: the modal stays mounted (`if (!open) return null` after hooks), and `draft`/`originalSettings` were initialized via `useState(currentSettings)` — that initial value is captured once at first mount, which happens before `App.tsx`'s async `loadSettings()` resolves, and is never re-applied after `saveSettings` updates the store → Rule: any modal/panel that stays mounted and seeds local draft state from a Zustand store must re-sync that draft (via `useEffect` keyed on the `open`/visibility prop) every time it opens, not just on first mount — `useState(storeValue)` only captures the value at that single render.

[2026-07-02] `git add -A` in a scoped Phase-8 commit swept in an unrelated pre-existing untracked file (`docs/prompt-remediation.md`, listed as `??` at session start), landing it on `main` via the merge → Root cause: used the blanket `git add -A` instead of staging the explicit paths the task touched, so any untracked file in the tree gets captured silently → Rule: when other untracked files exist in the working tree, stage explicit paths (`git add <path> …`), never `git add -A`/`git add .`; run `git status`/`git diff --cached --stat` before committing to confirm the staged set matches the task scope.
