# ADR-010 : jeu Wolf RPG déchiffré dans l'app par la crate unwolf

## Statut
Accepté — 2026-11-18 (plan UWF, `tasks/todo.md`, décisions UWF-D1 à UWF-D11). Complète ADR-008 : la lecture et
l'export d'un jeu Wolf ne changent pas ; seule la façon d'obtenir les fichiers libres de `Data/` change.

## Contexte
Depuis ADR-008, l'app ne lit un jeu Wolf RPG que depuis les fichiers libres de `Data/MapData/` et
`Data/BasicData/`, et refuse tant qu'une archive de texte (`Data.wolf`, `Data/MapData.wolf`,
`Data/BasicData.wolf`) est présente. L'utilisateur devait déchiffrer le jeu avec UberWolf (Windows), puis retirer
lui-même ces archives.

`unwolf` est un portage Rust d'UberWolf (MIT), publié sur crates.io, utilisable comme bibliothèque sans sa ligne de
commande (`default-features = false`). Sa version 0.2.0 a été préparée pour cette intégration : enums et
résultats publics `#[non_exhaustive]`, état de protection Pro distinct (« non Pro », « déjà déprotégé », V1, V2,
V3.5), gestionnaire d'événements `Send`, annulation par fichier.

## Décision
Quand l'ouverture d'un jeu échoue parce qu'il est encore empaqueté (`wolf_packed`) ou garde des archives de texte
(`wolf_archive_present`), l'interface propose de le déchiffrer **dans son dossier**, après une confirmation qui dit
ce qui change et conseille de travailler sur une copie (UWF-D1).

- **Archives extraites** (UWF-D2) : seulement celles qui contiennent du texte. `Data/BasicData.wolf` puis
  `Data/MapData.wolf` ; un `Data.wolf` racine est extrait en entier (le jeu doit alors tout lire en fichiers
  libres). Les archives d'images et de sons restent en place. Un fichier déjà présent n'est jamais remplacé.
- **Wolf RPG Pro** (UWF-D5) : l'état vient d'unwolf (`Session::protection_status`), jamais d'un test refait dans
  l'app. Non Pro ou déjà déprotégé : rien à faire ; protection 3.5 : levée (originaux dans
  `Data/BasicData/backup/`) ; V1, V2 ou état inconnu : refus, avant l'extraction des autres archives.
- **Contrôle** (UWF-D4) : avant de déplacer quoi que ce soit, le jeu doit être lisible par l'app (lanceur et
  fichiers de `Data/BasicData/`, une base qui déclare l'encodage, au moins une carte). unwolf ne contrôle pas
  qu'un dossier déjà présent est complet. `Data.wolf` à côté d'un `Data/` non vide : refus (extraction partielle
  possible, le jeu perdrait ses images et ses sons).
- **Mise de côté** (UWF-D3) : les archives de texte sont **déplacées, jamais supprimées**, dans
  `<jeu>/Hoshi2Star-archives/` avec leur chemin relatif, une fois tout extrait, la protection levée et le contrôle
  passé. Un déplacement en échec remet en place les archives déjà déplacées. Une annulation ne déplace rien.
- **Détection** (UWF-D7) : `detect_engine` ne change pas. Sur « moteur non détecté », `open_project` demande
  `engines::wolf::sources::packed_state` : lanceur + archive de texte sans fichiers libres ⇒ `wolf_packed`.
- **Commandes** : `unpack_wolf_game` (un seul déchiffrement à la fois, progression `h2s://wolf/unpack-progress`
  au plus toutes les 100 ms, rapport en valeur de retour) et `cancel_wolf_unpack`. Les clés Pro trouvées sont
  gardées dans `<données de l'app>/unwolf/UberWolfConfig.json` (UWF-D8).

### Frontière entre unwolf et l'app (UWF-D11)
unwolf reste un projet indépendant (dépôt, versions, tests et publication à part). Tout ce qui relève du format
Wolf (archives, clés, protection Pro, WolfX) vit dans unwolf, derrière son API publique. L'app ne garde que ses
règles : quelles archives extraire, où les mettre de côté, quand refuser, commandes, interface.

- **Un seul module de l'app importe unwolf** : `src-tauri/src/engines/wolf/unpack.rs` (et ses tests). Le reste de
  l'app ne voit que `unpack_game`, `UnpackReport`, `UnpackProgress` et `UnpackError`.
- La dépendance vient de crates.io : `unwolf = { version = "0.2", default-features = false }`, jamais un chemin
  ni une dépendance Git, jamais une copie du code.
- Un manque ou un défaut d'unwolf se corrige dans unwolf, puis l'app monte de version ; aucun contournement dans
  l'app.

**Mettre à jour unwolf.**
1. Correctif 0.2.x : `cargo update -p unwolf --manifest-path src-tauri/Cargo.toml` (le `Cargo.lock` fige la
   version entre deux mises à jour).
2. Version incompatible (0.3…) : changer la ligne de `src-tauri/Cargo.toml`, puis `cargo update -p unwolf`.
3. Lire le `CHANGELOG.md` d'unwolf ; adapter seulement `engines/wolf/unpack.rs`. Chaque `match` sur un type
   d'unwolf garde un bras générique qui refuse ou signale un échec, jamais un succès par défaut.
4. Mettre à jour la copie de licence `src-tauri/resources/licenses/unwolf-NOTICE.txt` si `LICENSE` ou `NOTICE`
   changent.
5. Gate complet (fmt, clippy, tests Rust et front), en session cloud.

## Conséquences
- Un jeu Wolf empaqueté (2.x, 3.x, Pro 3.5) s'ouvre sans outil externe. UberWolf, ou la commande `unwolf`, reste
  le recours pour Pro V1/V2 et pour un jeu que l'app refuse.
- Le dossier du jeu est modifié par l'app (fichiers libres ajoutés dans `Data/`, archives de texte déplacées) :
  d'où la confirmation et le conseil de copie. Les archives mises de côté sont une base possible de l'instantané
  d'origine Wolf (UW-D5, `BACKLOG.md`).
- Hypothèse à prouver en jeu (UWF-V) : le jeu ignore `Hoshi2Star-archives/` et lit les fichiers libres.
- Les branches Pro ne peuvent pas être fabriquées dans les tests (unwolf ne sait pas créer ces archives) : elles
  sont vérifiées sur de vrais jeux (UWF-0, UWF-V).
- Hors périmètre : polices WolfX et choix de la police d'ajustement (UWF-D6, `BACKLOG.md`) ; restauration des
  archives depuis l'app ; reconstruction d'archive à l'export.
- Le module `engines/wolf/decrypt/` reste du code mort ; retrait en lot séparé (UWF-7) après l'essai réel.
