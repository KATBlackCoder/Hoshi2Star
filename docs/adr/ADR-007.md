# ADR-007 : mises à jour in-app via tauri-plugin-updater (GitHub Releases + signature obligatoire)

## Statut
Accepté — 2026-07-02

## Contexte
Jusqu'à la 0.4.3, une nouvelle version obligeait l'utilisateur à retourner sur
la page GitHub Releases, télécharger l'artefact et réinstaller à la main. Aucun
signal in-app n'indiquait qu'une version existait. On veut : au démarrage,
détecter une version publiée plus récente, la proposer (Oui/Non), et si Oui la
télécharger avec une barre de progression puis redémarrer sur la nouvelle build.

Contraintes du format de distribution (Tauri) :
- Seuls **AppImage** (Linux) et **NSIS `.exe` / `.msi`** (Windows) sont
  auto-updatables. **`.deb` / `.rpm` ne le sont pas** (gérés par le gestionnaire
  de paquets système).
- L'updater Tauri **exige une signature minisign** : `createUpdaterArtifacts`
  produit un `.sig` par artefact et l'action CI signe avec la clé privée.

## Décision
Intégrer **`tauri-plugin-updater` v2** + **`tauri-plugin-process` v2** (pour
`relaunch()`), avec :

- **Endpoint** = `https://github.com/KATBlackCoder/Hoshi2Star/releases/latest/download/latest.json`.
  L'action `tauri-action` génère et uploade `latest.json` (+ `.sig`) sur la
  release. Simple, gratuit, aucune infra à héberger.
- **Signature obligatoire** : `bundle.createUpdaterArtifacts: true` +
  `plugins.updater.pubkey` (publique, dans `tauri.conf.json`). La clé **privée**
  vit hors dépôt (`~/.tauri/…`) et n'existe en CI que via le secret GitHub
  `TAURI_SIGNING_PRIVATE_KEY` (+ `_PASSWORD`). `.gitignore` bloque `*.key` /
  `.tauri/` en filet de sécurité.
- **UI gatée** par une commande Rust `updater_supported() -> bool`
  (`cfg!(target_os = "windows") || std::env::var_os("APPIMAGE").is_some()`) :
  sur une install non auto-updatable (deb/rpm, dev), l'UI d'update ne s'affiche
  jamais — pas de bouton menant à un chemin impossible.
- **Machine à états** côté front dans un store Zustand `updater`
  (`idle → checking → available → downloading → ready`, plus `dismissed` /
  `error`). Choix « Non » → `dismissed` : la version est **persistée**
  (tauri-plugin-store) pour ne pas re-proposer la même à chaque lancement ; un
  badge toolbar permet de rouvrir la décision. Une version **plus récente** que
  celle rejetée écrase le rejet.
- **Windows `installMode: "passive"`** : barre de progression native de
  l'installeur NSIS, sans assistant interactif.

## Alternatives rejetées
- **Serveur de manifeste dédié / dynamic update server** : plus de contrôle
  (canaux, rollout progressif) mais infra à héberger et maintenir pour zéro gain
  à notre échelle. GitHub Releases suffit.
- **Updates non signées** : impossible — le plugin refuse de s'initialiser sans
  pubkey dès que `createUpdaterArtifacts` est activé, et une update non signée
  est un vecteur d'exécution de code arbitraire.
- **Redémarrage automatique silencieux après download** : rejeté au profit d'un
  état `ready` explicite (« Redémarrer maintenant / Plus tard ») — on ne tue pas
  une session de traduction en cours sans consentement.

## Conséquences
+ Signal in-app + parcours Oui/Non/plus-tard sans quitter l'app ; redémarrage
  sur la nouvelle version en un clic (plateformes supportées).
+ Sécurité : toute update est vérifiée par signature avant installation.
+ Dette d'infra nulle (réutilise la release GitHub existante).
- **La signature devient un prérequis dur de CHAQUE release** : sans le secret
  `TAURI_SIGNING_PRIVATE_KEY` en CI, le build taggé `v*` échoue. La perte de la
  clé privée = plus aucune update possible pour les installs déjà déployées.
- **Ne bénéficie qu'aux versions futures** : la première build updater-enabled
  (0.4.4) s'installe manuellement ; l'auto démarre ensuite (0.4.4 → 0.4.5 …).
- **Dépendance opérationnelle** : `/releases/latest/` ignore les drafts et
  prereleases — l'update n'est servie qu'**après** publication manuelle de la
  release (notre workflow crée des drafts, `releaseDraft: true`).
- deb/rpm restent mis à jour via le gestionnaire de paquets, hors de ce flux.
